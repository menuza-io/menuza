# Voice agent deployment

`apps/voice-agent` is the LiveKit worker that answers phone calls for the AI
phone agent. In production it runs on
[LiveKit Cloud agent hosting](https://docs.livekit.io/deploy/agents.md) in the
`us-east` region (Ashburn, next to the US tenant-api). It handles US calls only:
the worker refuses to start unless `DATA_REGION=us`.

For the product design see [AI phone calling](./ai-phone-calling-plan.md). For
local development see its "Local development" section.

## Why LiveKit Cloud, not Cloudflare

The worker keeps a long-lived connection to LiveKit, holds realtime audio for
the whole call, and loads the native `@livekit/rtc-node` module. Cloudflare
Workers can't run it. Cloudflare Containers can run the image, but they sleep
when idle, can't be pinned to a location, and don't autoscale per call. LiveKit
Cloud runs the same image next to its SIP and media servers, scales it per call,
and rolls out new versions without dropping calls.

## How a deploy works

| Piece                                         | Purpose                                                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/voice-agent/Dockerfile`                 | Image LiveKit Cloud builds. Node 22, production dependencies only, runs as an unprivileged user, starts with `node --import=tsx src/main.ts start`.           |
| `apps/voice-agent/Dockerfile.dockerignore`    | Becomes `.dockerignore` in the uploaded directory (drops tests and `node_modules`).                                                                           |
| `apps/voice-agent/scripts/livekit-deploy.mjs` | `npm run deploy:livekit -w voice-agent`. Stages a pruned monorepo with `turbo prune voice-agent --docker` (about 2 MB) and runs the LiveKit CLI (`lk`) on it. |
| `deploy-voice-agent` job in `deploy.yml`      | On pushes to `main` that affect `voice-agent` (or `@repo/phone-agent`), after lint, typecheck, and unit tests pass, installs a pinned `lk` and deploys.       |
| `launch.voice-agent.env` (gitignored)         | Runtime secrets for the LiveKit agent, written by `npm run launch:setup`.                                                                                     |

LiveKit builds the image on its build service (10-minute limit, 1 GB upload
limit), then does a rolling deploy: new calls go to the new version once its
health check passes, and old instances get up to an hour to finish their calls.
If the new version never becomes healthy, the old one keeps answering.

The worker exits at startup in production when its config is unusable: the
development `VOICE_AGENT_TOKEN`, a non-HTTPS or local `APP_URL` or
`TENANT_API_URL`, or a missing Deepgram, Gemini, or Cartesia key. A bad secret
therefore shows up as a failed rollout instead of failed calls.

Two details of the upload are handled by the script, so don't "simplify" them:

- LiveKit drops `.env.*` files from uploads. The varlock schema travels as
  `env.schema` and the Dockerfile renames it back to `.env.schema`.
- `lk` checks for `@livekit/agents` in a `package.json` at the root of the
  upload. The script writes a small one there; the image is built from `json/`
  and `full/`.

## Runtime secrets

Set on the LiveKit agent, not in GitHub. LiveKit Cloud injects `LIVEKIT_URL`,
`LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` itself; don't set them.

| Secret                          | Required | Notes                                                                                     |
| ------------------------------- | -------- | ----------------------------------------------------------------------------------------- |
| `DATA_REGION`                   | Yes      | Always `us`.                                                                              |
| `VOICE_AGENT_TOKEN`             | Yes      | 32+ characters. **Same value on App and the US tenant-api.** Generated by `launch:setup`. |
| `APP_URL`                       | Yes      | Public App origin, e.g. `https://app.example.com`.                                        |
| `TENANT_API_URL`                | Yes      | US tenant-api origin, e.g. `https://tenant-us.example.com`.                               |
| `DEEPGRAM_API_KEY`              | Yes      | Speech-to-text.                                                                           |
| `GOOGLE_API_KEY`                | Yes      | Gemini.                                                                                   |
| `CARTESIA_API_KEY`              | Yes      | Text-to-speech.                                                                           |
| `CARTESIA_DEFAULT_VOICE_ID`     | No       | Voice when a business hasn't picked one.                                                  |
| `PHONE_AGENT_LLM_MODEL`         | No       | Defaults to `gemini-2.5-flash`.                                                           |
| `LIVEKIT_SIP_OUTBOUND_TRUNK_ID` | No       | Enables warm transfers to staff. Without it, transfers are cold SIP REFERs.               |
| `RECORDING_S3_*`                | No       | Call recording bucket (LiveKit Cloud runs Egress). Must match the tenant-api bucket.      |

The script skips empty values, refuses a file without the required ones, and
never passes LiveKit's own credentials.

## First-time setup

1. **LiveKit Cloud project.** The free Build plan is enough to start and for a
   pilot: 1 agent, 5 calls at once, and 1,000 agent session minutes and 1,000
   third-party SIP minutes a month. Its catch is cold starts: the agent scales
   to zero when idle, and the first call after that waits 10 to 20 seconds,
   which callers hear as dead air. There is no instant rollback either (redeploy
   the previous commit instead). Move to Ship (from $50/month) once businesses
   rely on the phone agent; it keeps the agent warm and raises the limits.
2. **Review Observability.** In the LiveKit dashboard, open Project → Settings →
   Observability. When it's on, LiveKit stores transcripts, traces, and session
   audio in the project's data region. Our retention job and caller erasure
   can't reach that copy, so keep it off unless you have accepted that. The
   worker already starts sessions with `record: false`.
3. **Secrets file.** `npm run launch:setup` writes `launch.voice-agent.env` with
   a fresh `VOICE_AGENT_TOKEN` and your App and tenant-api URLs, and pushes the
   same token to App and the US tenant-api as Wrangler secrets. Fill in the
   provider keys.
4. **App secrets.** On the App Worker set `LIVEKIT_URL`, `LIVEKIT_API_KEY`,
   `LIVEKIT_API_SECRET` (test calls and dispatch), and optionally
   `CARTESIA_API_KEY` (voice picker).
5. **Create the agent.** Install the
   [LiveKit CLI](https://docs.livekit.io/reference/developer-tools/livekit-cli.md),
   then from the repo root:

   ```bash
   export LIVEKIT_URL=wss://<project>.livekit.cloud
   export LIVEKIT_API_KEY=<key> LIVEKIT_API_SECRET=<secret>
   npm run deploy:livekit -w voice-agent -- --create --secrets-file launch.voice-agent.env
   ```

   This builds and starts the first version in `us-east` (change with
   `--region`) and prints the agent ID.

6. **GitHub.** Variables `LIVEKIT_URL` and `LIVEKIT_AGENT_ID`; secrets
   `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`. Until all four exist the
   `deploy-voice-agent` job logs a notice and skips.
7. **Telephony.** Create the inbound SIP trunk and a dispatch rule that sends
   each caller to agent `phone-agent`, as described in the plan's "Real phone
   numbers (US)" steps. For warm transfers, create an outbound trunk and set
   `LIVEKIT_SIP_OUTBOUND_TRUNK_ID`.
8. **Verify.** `lk agent status --id <agent-id>` shows `Running`. Place a test
   call from `/{orgSlug}/phone-agent/test`, then a real call to the number.

## Day-to-day

```bash
# Ship the current checkout by hand (CI does this on main)
npm run deploy:livekit -w voice-agent

# Change or rotate secrets (rolling restart, active calls continue)
npm run deploy:livekit -w voice-agent -- --update-secrets --secrets-file launch.voice-agent.env

# Inspect the build context without deploying
npm run deploy:livekit -w voice-agent -- --stage-only --out /tmp/voice-agent-context

lk agent status --id "$LIVEKIT_AGENT_ID"
lk agent logs --id "$LIVEKIT_AGENT_ID"                  # runtime logs
lk agent logs --id "$LIVEKIT_AGENT_ID" --log-type build # build logs
lk agent versions --id "$LIVEKIT_AGENT_ID"
lk agent rollback --id "$LIVEKIT_AGENT_ID"              # Ship plan and up
```

**Rotating `VOICE_AGENT_TOKEN`:** App, the US tenant-api, and the agent must
agree, and calls fail while they don't. Re-running `npm run launch:setup`
generates a new token for every service; push it to the agent with
`--update-secrets` right after the Wrangler secrets are applied.

**Staging** is not wired. To add it, create a second agent (ideally in a
separate LiveKit project, since staging App and tenant-api URLs differ) and copy
the job with `_STAGING` variables for the `dev` branch.

## KSA (future)

KSA calls can't use this deployment. The residency rule in
[tenant data residency](./tenant-data-residency.md) says KSA customer PII must
not be stored or transited outside Saudi Arabia, and a call carries the caller's
voice, number, and often name and address.

What LiveKit Cloud offers today (checked October 2026):

- Agent hosting runs only in `us-east`, `eu-central`, and `ap-south`. There is
  no Saudi region, so the worker would run abroad.
- Realtime traffic can be pinned to the `me` region group, which spans Saudi
  Arabia **and the UAE**, so media could still leave the kingdom.
- SIP has a Saudi-only regional endpoint
  (`<sip-subdomain>.sa.sip.livekit.cloud`) and outbound calls can originate in
  Jeddah (`destination_country: "sa"`). That covers telephony, not the worker or
  observability data.

So KSA needs the self-hosted shape the plan already recommends. Same code and
same image, different infrastructure:

1. **Infrastructure in Riyadh (OCI).** LiveKit server, LiveKit SIP, Egress, and
   Redis on OCI VMs next to the KSA tenant-api, plus the voice worker as a
   container. The Dockerfile works outside LiveKit Cloud: stage the context with
   `--stage-only`, `docker build` it for `linux/arm64` (the lockfile already
   carries the arm64 native bindings), and set `LIVEKIT_URL`, `LIVEKIT_API_KEY`,
   and `LIVEKIT_API_SECRET` yourself. CI would mirror `container-tenant-api` and
   `deploy-tenant-api-oci`: push to GHCR, then SSH to the Riyadh VM.
2. **Carrier.** A CST-licensed in-kingdom SIP trunk whose media terminates in
   the kingdom (see the plan's Telephony table).
3. **Speech and model.** The open decision in the plan: self-hosted or
   in-kingdom STT, LLM, and TTS, or waiting for in-kingdom hosted models. GPU
   capacity in OCI Riyadh must be confirmed for the self-hosted path.
4. **Code changes.**
   - Replace `assertUsDataRegion` with per-region provider config in
     `src/models.ts`, so `DATA_REGION=ksa` selects in-kingdom plugins and
     anything else still refuses to start.
   - Extend `assertProductionConfig` with the KSA provider keys.
   - App: per-region LiveKit credentials (for example `LIVEKIT_URL_KSA`) for
     test-call tokens and dispatch, chosen by the organization's `dataRegion`.
     Today App only offers the phone agent to US organizations.
   - The KSA worker uses the KSA tenant-api (`TENANT_API_URL` set to the KSA
     origin) and a `VOICE_AGENT_TOKEN` distinct from the US one.
   - Link SMS needs an in-kingdom provider; Twilio is blocked for KSA.
5. **Recordings.** An OCI Object Storage bucket in-region (`RECORDING_S3_*` with
   the OCI S3-compatible endpoint).
6. **Exit check.** A test call traced end to end (SIP, media, worker, model
   calls, storage) with every hop inside Saudi Arabia, per phase 5 of the plan.

The US deployment is unaffected by all of this: LiveKit Cloud keeps running the
US worker, and KSA adds a second, self-hosted deployment.
